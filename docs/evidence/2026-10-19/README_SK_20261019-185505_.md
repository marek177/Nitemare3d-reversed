# Nitemare 3D – RE-RUNTIME NEXT: GUARD 41 po smrti (DOS V1.2), kontrola DOS V2.0

**19. 10. 2026 · výsledok: lokálny runtime PASS, úplný death lifecycle OPEN.**

Tento balík nadväzuje na predchádzajúci overený smrteľný zásah v pôvodnom DOS V1.2 (`GUARD HP 111→0`, skóre `0→100`, mapový marker `A5→00`, RNG #16–18). Pri prirodzenom prehrávaní **DEMO.1** bol spustený pôvodný nepatchovaný `N3D.EXE` v DOSBox-X N3D Advanced History v3. Po smrti sa sledoval pôvodný GUARD 41 na `264B:2A78`, jeho stav na `264B:2A83`, pripojený WORLD objekt `264B:1C06`, skóre na `DS:40DE` a RNG na `DS:24A6`.

## 1. Nový pôvodný runtime – skutočné prechody

- **State0 → State9:** skutočná zmena zachytená `BPM 264B:2A83`, s pamäťovými dumpmi a debugger screenshotom. Pôvodný handler `0CC6:0DCE` znižuje timer (`0CC6:0DF4`) a po jeho vypršaní vykonáva `MOV [BX+0B],AL` z `GUARD+0C=09` (`0CC6:0DFF–0E05`). Ide o originálny opcode a prirodzene dosiahnutý výsledok; **nemáme súvislý instruction trace všetkých troch update volaní**.
- **State9 → State0A:** ďalší breakpoint na **`103C:031B`** pri zapísanom stave `0A`. Originál vykonal `0CC6:1013 CALL FAR 103C:0300`, potom `103C:030E OR ES:[SI+05],01` a `103C:0316 MOV ES:[DI+0B],0A`. Obe pamäťové operácie sú v krátkom originálnom `.n3dt`.
- **WORLD flag:** pôvodné `WORLD+05` bolo `0B`, a operácia OR dala znovu `0B`. Tento konkrétny zápis teda nepridal nový bit. **Nepreukazuje ani drop predmetu, ani jeho neprítomnosť neskôr.**
- Počas štyroch zachytených kontrolných bodov zostalo HP=0, skóre=100, RNG=`AEA69ED3`, prepojený mapový marker zostal nulový.

### Presná hranica CPU dôkazu

`trace/trace-000000.n3dt` má **80 kompletných udalostí, z toho 17 vykonaných CPU inštrukcií**: od `0CC6:1006` po **inštrukciu zápisu** na `103C:0316`. Záznam skončil `PROCESS_EXIT` po ukončení problémového automatizovaného debugovacieho behu, **nie** `USER_STOP`. Všetkých 80 uložených udalostí je validne parsovateľných, ale *nezachytávajú zvyšok state9 handlera po zápise `0A`*. Neprezentovať ich ako dokončenie celého death/drop/OBJECT cleanup cyklu.

Naopak predchádzajúci dôkazový ZIP `N3D_GUARD41_DEATH_SCORE_ADVANCED_V3_20261019.zip` obsahuje úplný samostatný `USER_STOP` trace smrteľného zásahu až po vymazanie mapového markeru. Tento nový balík je **oddelený ďalší runtime priechod**, nie pokračovanie identickej inštancie DOSBox-X.

## 2. DOS V1.2 versus V2.0 – presná statická kontrola originálnych EXE

Pôvodné rozbalené EXE súbory boli porovnané priamo po SHA-256 identifikácii:

| Lokálne telo | DOS V1.2 EXE file offset | DOS V2.0 EXE file offset | Zhoda |
|---|---:|---:|---:|
| `state0` handler | `0x59EE` | `0x5C3C` | **62/62 bajtov** |
| `state9` handler | `0x5C26` | `0x5E74` | **95/104 bajtov** |
| prolog WORLD terminal helpera | `0x8680` | `0x88DC` | **27/27 bajtov** |

DOS V1.2 a V2.0 majú v `state0` **úplne identických 62 bajtov** vrátane lokálneho testovania animačných hraníc, decrementu timeru a writeru nasledujúceho stavu. Deväť rozdielov v 104-bajtovom `state9` úseku sa nachádza v operandoch adries/cieľov volania a referencií na stavovú pamäť; nejde o dôkaz identického globálneho správania. Presnú kontrolu vykonáva `verify_postdeath.py --dos12 ... --dos20 ...`.

Oba dispatchery mapujú `state 0x0A` na spoločný návratový epilóg (v príslušnej verzii). Z toho však nevyplýva okamžité fyzické uvoľnenie GUARD slotu v celom engine, pretože ďalší scheduler/cleanup kód môže existovať inde.

**DOS V2.0 runtime smrti GUARD 41 zatiaľ NEBOL potvrdený.** Pokus o prirodzený DEMO breakpoint sa nepodarilo úspešne dokončiť pre problém automatizovaného ovládania emulátora. Preto tu máme **runtime iba DOS V1.2 + statický DOS V1.2/V2.0 diff**.
