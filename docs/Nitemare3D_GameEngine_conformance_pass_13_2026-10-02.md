# Nitemare 3D — Game Engine conformance pass 13
## OpenNitemare3D renderer migration: VEC/owner/span stage 1
Date: 2026-10-02

## Result

The first implementation migration away from the current OpenNitemare3D
floating-point DDA renderer is prepared.

The migration is opt-in and wall-only. It does not overwrite the legacy path by
default.

## Instruction-backed core ported

The new C# `OriginalRendererCore` includes:

- original 304×152 viewport geometry;
- exact projection-constant calculation;
- original VEC and span semantic layouts;
- exact orientation-dependent owner replacement matrix;
- exact signed 16.16 span initializer;
- exact texture-U endpoint correction;
- exact wall-height sampling/clipping-table generation;
- indexed wall-column output;
- original orientation-list comparator;
- original renderer capacity limits.

## Bridge integration added

The experimental renderer now constructs axis-aligned wall VECs from the
existing OpenNitemare3D tilemap and uses them through:

```text
VEC -> orientation lists -> projection
    -> owner buffer -> spans -> wall columns
```

Adjacent compatible tile edges are merged by 64 internal units, matching the
role of original `FUN_1018_4006`.

Orientation endpoints use the recovered original numbering:

```text
0 top edge    : (x,y)     -> (x+1,y)
1 bottom edge : (x,y+1)   -> (x+1,y+1)
2 right edge  : (x+1,y)   -> (x+1,y+1)
3 left edge   : (x,y)     -> (x,y+1)
```

all at 64 internal units per tile.

## Player-outward list traversal

The orientation lists use the recovered sort rule:

- horizontal vectors sort by Y;
- vertical vectors sort by X.

Stage 1 then traverses:

- orientation 0 forward from player Y;
- orientation 1 backward below player Y;
- orientation 2 backward left of player X;
- orientation 3 forward from player X.

This mirrors the direction of the four initial list walks visible in
`FUN_1018_3940`.

## Intentionally not labeled exact yet

The OpenNitemare3D bridge still lacks the original wall-property/class byte
tables used by VEC generation.

It also uses transformed-space near clipping and and geometric inverse wall
intersection before the exact `6422` U correction.

Those two sections are explicitly isolated with they can be replaced without
changing the exact low-level owner/span/sampling core.

## Important implementation consequence

The current legacy sprite renderer depends on and floating zBuffer generated by
the old DDA wall loop.

Stage 1 therefore does not draw legacy sprites when the VEC renderer is active.

Mixing the legacy sprite zBuffer path with the original owner-buffer wall path
would create false parity evidence.
