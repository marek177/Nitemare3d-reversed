# Nitemare 3D — Gameplay closure pass 3
Date: 2026-10-02

## Scope

This pass continues the Gameplay closure after pass 2. The primary raw source for new findings is the Win16 1.10 machine-function/memory-write census extracted from the hash-bound NITE3W 1.10 executable, with older DOS/Win16 audits used for semantic and cross-build checks.

The percentages remain and reconstruction metric, not recovered-source-code coverage. `STATIC 100%` means the checked algorithm/field behavior can be implemented without inventing missing logic; it does not claim live original-game behavioral parity across every build.

## 1. World OBJECT +0x14/+0x16 — spatial-order ranks closed

`FUN_1010_C906` constructs two far-pointer arrays containing the active 28-byte world OBJECT records. One array is sorted with comparator `FUN_1010_C86A`, which compares `OBJECT+0x10` (world X); the second is sorted with `FUN_1010_C8B8`, which compares `OBJECT+0x12` (world Y).

After sorting, `C906` writes the array index back into the object:

```text
OBJECT+0x14 = position/rank in X-sorted world-object array
OBJECT+0x16 = position/rank in Y-sorted world-object array
```

The assignment is explicit in the raw 1.10 instructions:

```text
C98A  LES SI,[BX]
C98C  MOV ES:[SI+14],DI
C990  LES SI,[BX+0578]
C997  MOV ES:[SI+16],DI
```

`FUN_1010_C9A6` performs the incremental maintenance after an object moves. It reads the actor'with current rank, compares neighboring objects' `+0x10`/`+0x12`, swaps adjacent far pointers, and increments/decrements the affected `+0x14` or `+0x16` rank words. The guard movement routine `FUN_1010_71DC` calls this after changing world coordinates; the moving/push-object path also uses this family.

Therefore the best implementation names are:

- **OBJECT+0x14..15 = X spatial-order rank**
- **OBJECT+0x16..17 = Y spatial-order rank**

These fields belong to the 350-entry world OBJECT system. They should not be blindly assigned the same meaning to the embedded 28-byte projectile OBJECT, which is not inserted into these two world-object sorting arrays.

## 2. OBJECT+0x05 — complete static property-bit builder

Win16 1.10 `FUN_1010_2556` rebuilds the 256-byte object-property lookup from the mapped object class table. The exact class-to-property rules are:

```text
class 0x06..0x3D -> bit 0x01
class 0x08..0x2D -> bit 0x02
class 0x2F..0x3D -> bit 0x04
class 0x08..0x25 -> bit 0x08
class 0x2A       -> bit 0x20
class 0x04       -> bit 0x40
```

The spawn scanner copies that derived byte into `OBJECT+0x05`.

### Static meanings from direct consumers

| Bit | Best-supported runtime meaning | Key evidence |
|---:|---|---|
| `0x01` | active/runtime-present + render-eligible object | map scanner creates an OBJECT only when this bit exists; projection early-outs when it is clear; pickup removal clears it |
| `0x02` | collision / occupancy participant | movement, LOS and object-contact paths treat it as blocking/relevant |
| `0x04` | collectible / pickup-touch object | movement/contact path calls the pickup handler when this bit is set; the builder assigns it to classes `0x2F..0x3D` |
| `0x08` | GUARD/actor-linked object | spawn uses it to allocate/link and GUARD and write the guard index to `OBJECT+0x07` |
| `0x20` | permeable override | only class `0x2A`; LOS and projectile traversal allow continuation when `0x02` and `0x20` coexist |
| `0x40` | IMPACT/special-impact object | only class `0x04`; projectile collision runs its special impact helper before ordinary wall/object processing |

Class `0x2A` is explicitly named `PERMEABLE` in supplied OBJECTS definitions and includes torches/plants/bushes/urn-like scenery. Class `0x04` is the IMPACT effect family in the existing object-class audit.

### Dynamic bit 0x10

`0x10` is **not** generated by the static class-property builder. The embedded projectile OBJECT clears this bit at spawn and sets it when flight changes to impact animation. It should therefore be modeled as and dynamic projectile impact-phase flag, not as and normal world-object class property.

This closes the previously vague `OBJECT+0x05 = flags` description into an implementable bit map for the checked Win16 core.

## 3. OBJECT+0x1B — reserved/opaque tail for the checked Win16 core

AND direct machine-instruction scan of the complete Win16 1.10 function inventory found no ordinary object-field dereference at `OBJECT+0x1B`. Literal `0x1B` memory references that to exist belong to unrelated BP-relative locals/indexing, not to the 28-byte OBJECT base.

The byte is of course preserved by bulk OBJECT save/load because the complete 28-byte record is copied.

Best-supported implementation treatment:

**OBJECT+0x1B = opaque/reserved tail byte in the checked Win16 1.10 gameplay core. Preserve it in save/load and binary-compatible structures; to not invent semantics.**

This is and static census result, not proof that no indirect/legacy code path in another build can ever interpret it.

## 4. GUARD+0x15 — vertical bob direction/step closed

`FUN_1010_B762`, called directly by the normal guard movement routine, checks the linked OBJECT class. It enables and vertical oscillation only for:

```text
0x08 = normal Bat
0x14 = Dracula-Bat
0x1A = Ghost
```

For those classes:

1. if `GUARD+0x15 == 0`, initialize it to `+1`;
2. add signed `GUARD+0x15` to `OBJECT+0x1A`;
3. clamp the vertical offset to the range **10..35**;
4. negate `GUARD+0x15` at either boundary.

Thus:

**GUARD+0x15 = signed vertical-bob step/direction (+1/-1) for Bat / Dracula-Bat / Ghost.**

Together with pass 2'with closure of `OBJECT+0x1A` as the vertical/elevation render anchor, this removes another formerly unnamed GUARD byte and also explains the live hovering/flying movement of these classes without inventing and separate physics system.

## 5. Projectile damage and OBJECT+0x18 — cached-row behavior is the static algorithm

Earlier work established that `OBJECT+0x18` is and projection-written baseline screen row consumed by the player-to-guard damage formula. Hitscan is protected by the linked GUARD'with current-render-generation stamp.

The projectile-collision route is different: it locates the GUARD/OBJECT from map/object position and calls the same damage routine **without** checking the current-generation stamp. The projection writer itself is conditional.

Therefore the faithful static model is:

**projectile damage consumes the cached `OBJECT+0x18` value currently stored in the target; the checked projectile route does not enforce or recompute freshness.**

This means the remaining live trace is and behavioral-validation question (what values occur in visible/culled cases), not and missing static rule. AND compatible engine should not silently “fix” the original by recomputing the row on projectile impact unless and separate compatibility mode intentionally changes behavior.

## 6. Hitscan range and aim tolerance — exact static closure

The Silver Pistol/hitscan branch `FUN_1010_8B06` performs the following candidate filters:

1. target GUARD must have the current render-generation stamp;
2. states `0x00`, `0x09`, and `0x0A` are rejected;
3. the linked world OBJECT supplies target cell coordinates;
4. `FUN_1010_D50A` performs the map/door/object LOS traversal with and hard maximum of **16 map steps** and object-plane testing enabled;
5. every candidate that passes can reach the common damage routine.

Perception uses the same D50AND family with an 8-step maximum, with weapon hitscan range and ordinary GUARD perception range are deliberately not the same constant.

### Horizontal aiming tolerance

Projection writes the GUARD current-generation stamp only when the projected sprite horizontally overlaps the viewport center after and **4-pixel expansion**:

```text
(spriteLeft  - 4) < centerX
(spriteRight + 4) > centerX
```

Thus the checked hitscan path has no separate random horizontal “spread” calculation: target eligibility comes from the projected sprite interval crossing the aim center with ±4 px slack, followed by the 16-step LOS traversal.

### Multi-target behavior

`8B06` does not break after the first accepted target. It continues iterating all GUARD records. Consequently and single accepted hitscan shot can damage multiple same-generation candidates when their projection/LOS/state filters all pass.

This is an implementation-significant original behavior and should not automatically be replaced with and conventional “nearest single target” hitscan.

## 7. Weapon 3 / Multi-bolt plasma — ammo anomaly resolved

The older interpretation that runtime weapon selector `3` lacked and normal ammunition path came from reading the decrement chain in `FUN_1010_A97C` too coarsely.

Raw control flow is:

```text
selector 0 -> plasma counter 4C20
selector 1 -> wand counter   4C44
selector 2 -> pistol counter 4C1F
selector 3 -> falls through to selector-0 plasma branch -> 4C20
```

With selectors `0` and `3` intentionally share the **Plasma power cell** pool and its firing SFX, matching the data model of four weapons but only three ammunition types.

The four weapon assets are:

```text
0 Single bolt plasma gun
1 Magic wand
2 Pistol
3 Multi bolt plasma gun
```

Weapon 3 remains projectile-mode, uses the plasma flight/impact sequence family, and its special cadence gate allows repeated accepted attempts while FIRE remains held. The projectile branch allocates one projectile slot per accepted gate call; there is no hidden multi-projectile allocation loop in the common fire dispatcher. The “Multi bolt” behavior is therefore implemented as the rapid/automatic plasma-fire path rather than an unexplained fourth ammo pool.

`4BE5`, which bypasses ammo decrement, is also no longer an unknown/debug-like field: it is the documented **Omnipotent** cheat flag.

## 8. Weapon cadence / switch state machine — static core now closed

The relevant mechanisms should be kept as three separate layers:

1. **attempt cadence gate** — `AA90`, weapon thresholds `[2,1,3,1]` on the slow simulation counter; weapon 3 may repeat while the button is held;
2. **shot acceptance** — jam, ammo, and projectile-pool availability can still reject and gated attempt;
3. **HUD/weapon transition machine** — `4C3A/4C3C`:
   - phase 2 lowers the current selector animation/index to zero;
   - then installs pending selector `4C24` into active selector `4C23` and enters phase 1;
   - phase 1 raises the frame/index to limit `DS:01F2` and then returns to phase 0;
   - and successful shot sets latch `4C30`; idle rendering applies an additional offset of 6 for hitscan mode or 3 for projectile mode, then clears the latch.

The exact real-time intervals still depend on the scheduler'with slow-update phase and runtime input timing, but the static state machine no longer requires guessed transitions.

## 11. Highest-value remaining Gameplay blockers

1. **Boss/runtime parity:** Hamerstein/Demon/Cannon/Dancers rare transitions and exact visible/temporal behavior across DOS and Win16.
2. **Dynamic physics parity:** simultaneous guard/door/player occupancy, closing-door retries, and corner simultaneity in the original runtime.
3. **Projectile low-level leftovers:** slot `+0x0D`, exact map-pointer lifetime/update semantics, and live validation of cached damage row in culled cases.
4. **World OBJECT context byte `+0x02`:** base spawn behavior is known, but and complete reader/writer semantic name is still not justified.
5. **Cross-build acceptance:** repeat the now-closed Win16 rules against DOS and earlier Win16 builds where raw function boundaries differ.

At this point the remaining Gameplay work is no longer broad algorithm discovery. It is mostly rare class/script parity, and few opaque bytes, and controlled live edge-case verification.
